The Unified Persistence & Hybrid Search Store (System 8) replaces the PREBUILT flat-file JSON storage with a single **PostgreSQL 16 + pgvector** database running locally on your Mac host via Homebrew rather than in a Docker container. It acts as the single source of truth, combining relational schema enforcement, biometric and semantic vector indexing, an immutable audit trail, and hybrid search retrieval.

**1. Relational Integrity & Safe Data Lifecycle**

- **Entity Relationships:** Persists the 12 core tables (`PROJECTS`, `MEETINGS`, `ATTENDEES`, `TRANSCRIPTS`, `MEETING_SUMMARIES`, `MEETING_DECISIONS`, `ATTENDEE_STORYLINES`, `TASKS`, `TASK_AUDIT_LOG`, etc.) with strict foreign keys.
- **Cascading Cleanup:** Applies `ON DELETE CASCADE` across transcripts, summaries, decisions, and storylines so that when a meeting's audio is moved to macOS `~/.Trash` via `send2trash`, all related artifacts are purged without leaving orphan records.
- **Operational Indexing:** Uses composite B-tree indexes—such as `(project_id, due_date, lifecycle_status)` on `TASKS`—to allow the SwiftUI calendar picker to query date ranges across years, months, and days with minimal latency.

**2. Specialized Multi-Vector Storage (pgvector)**

- **Acoustic Speaker Biometrics:** Stores 512-dimensional x-vector embeddings (`ATTENDEES.voice_embedding vector(512)`) generated by pyannote/ResNet34. Vector cosine distance (`<=>`) identifies returning speakers across meetings.
- **Task Semantic Embeddings:** Stores 384-dimensional dense vectors (`TASKS.embedding vector(384)`) generated by `all-MiniLM-L6-v2`. The reconciliation engine queries this to detect semantic overlaps before creating duplicate tasks.
- **Transcript Vectors:** Stores 384-dimensional passage embeddings on `TRANSCRIPTS` indexed with HNSW (`hierarchical navigable small world`) for sub-millisecond approximate nearest neighbor (ANN) retrieval.

**3. Hybrid Search Engine (Dense + Sparse with RRF)**

Semantic embeddings excel at conceptual meaning but frequently fail on exact names, dates, or technical codes. The store executes a combined hybrid search query using Common Table Expressions (CTEs) within PostgreSQL:

- **Dense Leg:** Retrieves top candidate passages using pgvector cosine distance (`ORDER BY embedding <=> query_vector`).
- **Sparse Lexical Leg:** Searches PostgreSQL full-text search (`tsvector @@ plainto_tsquery('english', query_text)`) scored by `ts_rank` via GIN indexes.
- **Reciprocal Rank Fusion (RRF):** Merges both result sets into a single unified ranking using:
    $$RRF(d) = \sum_{m \in M} \frac{1}{k + \text{rank}_m(d)}$$
    (with standard smoothing constant $k = 60$). This produces a balanced relevance score independent of disparate raw score scales, ensuring that exact keyword matches and semantic hits surface together.

**4. Project Scoping & Strict Context Isolation**

Every database read, write, and RAG retrieval strictly enforces a `WHERE project_id = :project_id` predicate. This prevents cross-project data contamination, guaranteeing that chat queries only retrieve evidence from meetings belonging to the active project boundary.

**5. Immutable Audit Log & State Reversibility**

Powers the 3-state task lifecycle (`open`, `done`, `dropped`) by logging every change to `TASK_AUDIT_LOG` with a unique `revert_token` and serialized before/after states. Reverting an accidental task drop or completion verifies the token and restores the prior state without mutating historical logs.
